How it works

Four steps from request to closed

Every request moves through the same path, and everyone involved can see where it stands.

  1. Raise

    A Help Seeker picks a category and describes what is needed. The request is saved.

  2. Notify

    Donors and volunteers are told right away that a new request is open.

  3. Respond

    A donor offers a donation or a volunteer accepts the task. The status changes and the seeker is notified.

  4. Close

    Once help is given, the seeker closes the request. If nobody responds, it stays open.

Who it is for

Four roles, one platform

Help Seeker

Someone who needs blood, food or a hand.

Raises requests, tracks status, closes them.

Donor

Someone who can give blood, food or other support.

Sees open requests, offers a donation.

Volunteer

Someone who can give time and effort.

Accepts tasks, coordinates help.

Administrator

The person who keeps the platform healthy.

Manages users and requests, reads activity reports.

Live demo

Be each user for a minute

Pick a role, raise a request as a Help Seeker, then switch to Donor or Volunteer to answer it. Switch back to see the notification and close it.

The demo runs in your browser and keeps its data on this device only. The full system stores everything in MySQL.

How it is built

Four layers, one request path

The structure follows the project's sequence diagram, so every screen action maps to a call you can trace.

Web UI

Forms, request lists and dashboards in the browser.

RequestController

Receives each HTTP call and passes it on.

RequestService

Applies the rules, updates status, raises notifications.

MySQL

Users, requests, responses and notifications.

Raise a request  POST /requests → createRequest(data) → save request → confirmation
Answer a request  GET /requests → getRequests() → fetch → list · POST /responses → addResponse() → save + update status → notification

Planned next: location-based matching, SMS and email alerts, and verification of donors and volunteers.
